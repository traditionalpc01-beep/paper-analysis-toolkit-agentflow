# PaperInsight v3.2 迭代需求文档

> 基于 2026-03-24 全量代码审查生成

---

## 一、审查总结

本次对 `paperinsight/` 全部核心模块、`desktop_bridge.py`、`cli.py`、`tests/`、以及 `docs/` 下的质量门禁文档进行了逐文件审查。审查覆盖代码质量、架构设计、异常处理、测试覆盖率、安全性、性能瓶颈和文档一致性等维度。

总体评价：项目在 Agent-First 改造后，架构分层清晰、质量门禁机制合理、IF 链路逻辑严谨。但在以下几个方面存在明确的改进空间，按优先级分为 P0（必须修复）、P1（强烈建议）、P2（建议优化）三个等级。

## 二、P0 - 必须修复的问题

### 2.1 pipeline.py `_supplement_impact_factor` 方法过于庞大且难以维护

**文件**: `paperinsight/core/pipeline.py` 第 479-626 行

**问题**: `_supplement_impact_factor` 方法体超过 150 行，包含多层嵌套的 if-else 分支（官方 IF -> NO_ACCESS -> 次级来源验证 -> AI 模型回退 -> 原有方式回退），逻辑路径极多，且多处出现重复的 `_resolve_journal_metadata` 调用和 `any([self.letpub_if_fetcher, self.if_fetcher, ...])` 检查。

**风险**:
- 新增 IF 来源或调整优先级时，极易遗漏分支导致数据不一致
- 单元测试难以覆盖所有路径组合
- 回退链路过长，任何一环的异常都可能被外层 `except Exception` 吞掉

**需求**:
- 将 `_supplement_impact_factor` 拆分为职责单一的小方法，建立清晰的 IF 获取策略链（Chain of Responsibility 或 Strategy 模式）
- 每个 IF 来源的 lookup 应封装为独立对象，统一接口 `lookup(journal_info) -> ImpactFactorLookupResult`
- 消除重复的 `any([...])` 检查，改为 `self._has_any_if_fetcher()` 属性
- 策略链的优先级顺序应可通过配置调整

---

### 2.2 异常处理过于宽泛，多处 `except Exception` 吞没关键信息

**文件**: 多个核心模块（pipeline.py、extractor.py、cli.py、desktop_bridge.py 等）

**问题**: 项目中共有超过 88 处 `except Exception` 捕获，其中多处存在：
- `except Exception: pass` 完全吞没异常（如 pipeline.py 第 207 行缓存加载、第 966 行批量处理）
- 仅记录 warning 级别日志但不向上传播（如 pipeline.py 第 625 行整个 `_supplement_impact_factor` 的外层 catch）
- 无法区分可恢复错误（如网络超时）和不可恢复错误（如数据损坏）

**风险**:
- 网络超时、API 限流等可恢复错误与数据格式错误等不可恢复错误无法区分
- 调试困难，生产环境问题定位依赖大量 warning 日志人工排查
- 缓存数据损坏时静默跳过，用户不知道结果可能是陈旧的

**需求**:
- 定义项目级异常体系（`PaperInsightError` 基类 + `ParseError`、`ExtractionError`、`IFLookupError`、`NetworkError` 等子类）
- 消除所有 `except Exception: pass`，改为至少记录 error 级别日志
- 区分可恢复与不可恢复错误：可恢复错误（网络超时、限流）向上抛出并允许重试；不可恢复错误记录 error 并继续处理下一个文件
- 为 `_supplement_impact_factor` 外层 catch 添加 error 级别日志而非 warning

---

### 2.3 `_should_try_secondary_if_sources` 方法未被使用

**文件**: `paperinsight/core/pipeline.py` 第 920-925 行

**问题**: `_should_try_secondary_if_sources` 是一个 `@staticmethod`，在整个项目中没有任何调用方。该方法判断是否应该尝试次级 IF 来源，但其判断逻辑（status in `{"ERROR", "NO_MATCH", ...}`）与当前 `_supplement_impact_factor` 的实际分支逻辑不一致。

**需求**:
- 如果该方法的设计意图已被新逻辑取代，删除该死代码
- 如果仍有价值，将其集成到 IF 策略链中

---

### 2.4 `to_excel_row()` 与 `REPORT_COLUMNS` 的字段映射关系脆弱

**文件**: `paperinsight/models/schemas.py`（`to_excel_row`）、`paperinsight/core/reporter.py`（`REPORT_COLUMNS` + `FIELD_MAPPING`）

**问题**: Excel 导出链路涉及三层映射：
1. `PaperData.to_excel_row()` 输出中文 key 的字典
2. `ReportGenerator.FIELD_MAPPING` 将规范化 key 映射到中文 key
3. `ReportGenerator.REPORT_COLUMNS` 定义最终导出列

三层映射之间没有自动化校验。`to_excel_row()` 返回 28 个字段，`FIELD_MAPPING` 有 30 个 key，`REPORT_COLUMNS` 有 22 列。新增字段时需要在至少两处同步修改，且当前无测试覆盖"所有 REPORT_COLUMNS 的 field_key 都能通过 FIELD_MAPPING 或 to_excel_row 找到对应值"。

**风险**:
- 新增导出列时容易遗漏映射，导致 Excel 中该列始终为空
- 删除/重命名字段时无法自动发现断裂的引用

**需求**:
- 建立字段映射的自动校验测试：验证 `REPORT_COLUMNS` 中每个 field_key 都能在 `FIELD_MAPPING` 或 `to_excel_row()` 中找到来源
- 考虑将三层映射简化为两层：`PaperData` 直接提供 `REPORT_COLUMNS` 对应的 key-value 字典

## 三、P1 - 强烈建议改进的问题

### 3.1 AnalysisPipeline 构造函数承担过多职责

**文件**: `paperinsight/core/pipeline.py` 第 50-150 行

**问题**: `__init__` 方法约 100 行，直接初始化了 6 个不同的 web fetcher（journal_resolver、if_fetcher、letpub_if_fetcher、search_crawler_fetcher、wos_if_fetcher、ai_model_if_fetcher），每个 fetcher 都有独立的配置读取和条件判断逻辑。Pipeline 既是编排器又是工厂。

**需求**:
- 将 fetcher 初始化逻辑提取到独立的工厂类或 builder（如 `IFSourceFactory`）
- Pipeline 构造函数只接收已初始化的依赖（依赖注入），而非自己创建

---

### 3.2 缓存机制缺少版本兼容性控制

**文件**: `paperinsight/core/pipeline.py` 第 200-208 行、`paperinsight/core/cache.py`

**问题**: 当前缓存通过 MD5 做 key，加载时尝试 `PaperData(**cached_result)` 反序列化。当 `PaperData` 的 schema 发生变更（新增/删除/重命名字段）时，旧缓存会因 `ValidationError` 被静默丢弃（`except Exception: pass`），但没有任何迁移机制或版本标记。

**需求**:
- 在缓存数据中加入 schema 版本号（如 `_cache_version: 1`）
- 加载缓存时检查版本，版本不匹配时记录 info 日志并标记缓存过期
- 提供缓存迁移钩子，允许在 schema 变更时自动转换旧缓存

---

### 3.3 `extractor.py` 文件过长（1518 行），职责过多

**文件**: `paperinsight/core/extractor.py`

**问题**: 单个文件 1518 行，包含 LLM 提取、正则提取、标题/作者/期刊/IF/EQE/CIE/寿命/器件/优化策略等十多种不同的提取逻辑，以及期刊别名表（约 40 行）、标题评分算法、器件去重和排序逻辑。违反单一职责原则。

**需求**:
- 将期刊相关逻辑（别名表、标准化、ISSN 提取）提取到 `journal_utils.py`
- 将器件相关逻辑（提取、去重、排序、评分）提取到 `device_extractor.py`
- 将标题/作者提取逻辑提取到 `metadata_extractor.py`
- `extractor.py` 只保留 LLM/regex 提取的编排逻辑

---

### 3.4 CLI 和 Desktop Bridge 的配置拼装逻辑大量重复

**文件**: `paperinsight/cli.py`（`analyze` 函数，第 260-444 行）、`paperinsight/desktop_bridge.py`（`_build_runtime_config`，第 340-376 行）

**问题**: CLI 的 `analyze` 命令和 Desktop Bridge 的 `command_analyze` 函数各自独立拼装运行时配置，包括：
- LLM provider 选择和初始化
- MinerU batch size 决策
- output format 合并
- bilingual 选项处理

两处的逻辑高度相似但不完全一致，新增配置项时需要同时修改两处。

**需求**:
- 提取公共的运行时配置构建器（`RuntimeConfigBuilder`），CLI 和 Desktop Bridge 都使用同一个 builder
- LLM provider 初始化也应统一（CLI 中约 40 行的 provider 分支判断可以直接复用）

---

### 3.5 `_generate_reports` 中错误行的列名硬编码

**文件**: `paperinsight/core/pipeline.py` 第 1182-1207 行

**问题**: 当 PDF 处理失败时，`_generate_reports` 手动构造一个包含所有列名的空字典。这个字典的 key 列表与 `ReportGenerator.REPORT_COLUMNS` 完全独立维护。如果 `REPORT_COLUMNS` 新增或删除列，错误行不会自动同步。

**需求**:
- 错误行字典应由 `ReportGenerator` 提供（如 `ReportGenerator.empty_result_row()`），确保列一致性

---

### 3.6 缺少对 `desktop_bridge` 返回结构的快照测试

**文件**: `tests/test_desktop_bridge.py`、`docs/KNOWN_GAPS.md` 第 22 行

**问题**: `desktop_bridge` 的每个 command（config-get、env-info、analyze）都通过 stdout 输出 JSON 协议，但当前测试只验证了 config-get 的基本结构，缺少对 env-info 和 analyze 返回结构的完整校验。KNOWN_GAPS 已记录此问题但未解决。

**需求**:
- 为 `env-info` 的返回结构添加快照测试（至少覆盖 `checks`、`recommendation`、`readiness` 三个字段的 key 完整性）
- 为 `analyze` 的 `progress`、`file-complete`、`completed` 消息类型添加结构测试

---

## 四、P2 - 建议优化的问题

### 4.1 缺少统一的 HTTP 请求重试和超时策略

**文件**: `paperinsight/web/` 下所有 fetcher（impact_factor_fetcher.py、journal_resolver.py、letpub_fetcher.py、search_crawler_fetcher.py、wos_journal_fetcher.py）

**问题**: 每个 web fetcher 都独立使用 `requests.Session`，各自处理超时，但没有统一的重试策略。部分 fetcher 在单次请求失败后不会重试（如 MJL lookup），而 LLM 客户端有 `max_retries` 配置。

**需求**:
- 创建统一的 `RetryableSession` 或 `http_client` 工具，封装重试逻辑（指数退避、最大重试次数）
- 所有 web fetcher 使用统一的 HTTP 客户端，而非各自创建 Session

---

### 4.2 `ImpactFactorLookupResult` 使用 `@dataclass(frozen=True)` 但 `pipeline.py` 中有大量 `getattr(result, ...)` 调用

**文件**: `paperinsight/web/impact_factor_fetcher.py`、`paperinsight/core/pipeline.py`

**问题**: `ImpactFactorLookupResult` 是 frozen dataclass，提供了完整的类型注解和属性访问。但 `pipeline.py` 中几乎所有地方都用 `getattr(result, "status", None)` 而非 `result.status`。这不一致且降低了类型检查的效果。

**需求**:
- 统一使用属性访问（`result.status`）替代 `getattr` 调用
- 对于确实需要动态访问的场景，添加注释说明原因

---

### 4.3 配置验证不充分

**文件**: `paperinsight/utils/config.py`

**问题**: `normalize_config` 只做了深度合并和格式标准化，缺少对配置值的范围校验。例如：
- `timeout` 可以是负数或 0
- `max_input_chars` 可以是 0（导致所有文本被截断为空）
- `impact_factor_validation_tolerance` 可以是负数（导致验证永远失败）

**需求**:
- 为关键配置项添加范围校验（`positive_int`、`positive_float`、`enum_value` 等）
- 校验失败时给出明确的 warning 日志并回退到默认值

---

### 4.4 缺少性能监控和可观测性

**文件**: 全局

**问题**: 当前日志只记录了 `[Done] filename (Xs)` 这样的简单计时，缺少：
- 各阶段（解析、清洗、提取、IF 补全）的独立耗时
- IF 来源命中率和回退路径的统计
- 缓存命中率的统计

**需求**:
- 为 pipeline 各阶段添加独立的计时日志
- 在 `run()` 返回的 stats 中包含各阶段平均耗时
- 添加可选的性能摘要（如 `--verbose` 时打印各阶段耗时）

---

### 4.5 `extractor.py` 中的期刊别名表无法动态更新

**文件**: `paperinsight/core/extractor.py` 第 63-97 行

**问题**: `JOURNAL_TITLE_ALIASES` 和 `JOURNAL_DOMAIN_HINTS` 是类级硬编码字典，新增期刊别名需要修改代码。对于科研领域期刊更迭频繁的场景，维护成本高。

**需求**:
- 将期刊别名表提取到独立的 YAML/JSON 配置文件中
- 支持用户在自定义配置中追加期刊别名
- `journal_resolver.py` 中已有 `journal_metadata.py` 的 canonicalize 函数，应统一使用该机制

---

### 4.6 测试覆盖面不足

**文件**: `tests/`

**问题**: 当前 19 个测试文件主要覆盖：
- 质量门禁契约（3 个文件）
- IF fetcher 和 journal resolver（3 个文件）
- v3.1 功能回归（1 个文件）
- Desktop bridge（1 个文件）

缺少覆盖：
- `SectionFilter` 清洗器的边界场景
- `DataExtractor` 的 regex 提取路径（当前只有 LLM 路径的间接测试）
- `FileRenamer` 的各种模板格式
- 缓存版本不兼容的降级行为

**需求**:
- 为 `SectionFilter` 补充边界测试（空输入、纯噪声章节、超长输入）
- 为 `DataExtractor._extract_with_regex` 补充端到端测试
- 为 pipeline 的端到端处理补全 golden file 测试（KNOWN_GAPS 已提出但未实现）

---

### 4.7 根目录存在大量临时脚本文件

**文件**: 项目根目录（git status 中 untracked files）

**问题**: 根目录有 20+ 个临时脚本文件（如 `extract_one.py`、`create_excel.py`、`test_write.py` 等），这些文件不在版本控制中，但会让项目结构显得杂乱，也可能包含过时的代码模式。

**需求**:
- 将这些文件归档到 `.tmp_test/` 目录（该目录已存在）
- 在 `.gitignore` 中确保临时目录被忽略
- 在 CONTRIBUTING 或 AGENT_WORKFLOW 中约定"临时脚本应放在 `.tmp_test/` 目录"

---

### 4.8 `reporter.py` 中 `_coerce_if_value` 使用 `__import__("re")` 延迟导入

**文件**: `paperinsight/core/reporter.py` 第 393 行

**问题**: `re` 模块是 Python 标准库，没有理由延迟导入。使用 `__import__("re")` 而非文件顶部的 `import re` 会降低代码可读性，且每次调用都会执行 import 语句（虽然 Python 有模块缓存，但写法不规范）。

**需求**:
- 在文件顶部添加 `import re`，将 `__import__("re").search(...)` 改为 `re.search(...)`

## 六、实施原则

1. **先 P0 后 P1**: P0 问题直接影响数据准确性和可维护性，应优先修复
2. **每轮改动遵循 AGENT_WORKFLOW**: 先写 issue -> 再出 plan -> 实现 -> 补 tests -> 补 docs
3. **逐步重构**: P0 中的 2.1（IF 策略链重构）和 2.2（异常体系）可以并行推进，因为它们影响不同的代码区域
4. **保持测试绿色**: 每次重构后必须运行 `python scripts/check_agent_harness.py` + 相关 pytest 子集
5. **AH-007 继续推进**: IF 准确性相关的 issue 在本次审查中仍标记为 IN_PROGRESS，v3.2 的 2.1 重构完成后可以关闭该 issue
